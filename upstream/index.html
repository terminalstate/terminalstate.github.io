Fixed upstream

Bugs in open-source payment code where a payment ends in the wrong state: the customer is charged and gets no order, or the webhook is acknowledged and the provider stops retrying. Each was reproduced against the project's own code before it was reported, with a test in the project's suite or a harness in callback-audit.

Status as of 28 October 2026.

Fixed (18)

  • Bagisto · Razorpay: the order amount was truncated instead of rounded, so totals like ₹19.99 were charged but no order was placed. Fixed by my PR, merged 13 Oct. #11523 · PR #11524
  • Paid Memberships Pro · Stripe: the webhook answered 200 when re-fetching the event from Stripe failed, so Stripe never redelivered it. Fixed by my PRs, merged 14 and 15 Oct; the second covers scheduled webhook runs. #3889 · PR #3890 · PR #3898
  • FOSSBilling · Stripe: subscription renewals were never recorded after the first invoice, so Stripe charged the customer and the renewal invoice stayed unpaid. Fixed by my PR, merged 16 Oct. #4522 · PR #4523
  • FOSSBilling · Stripe currencies: in COP, HUF, IDR, ISK, PKR, UGX and seven other currencies the total is sent to Stripe in the wrong unit, so the customer is charged 1/100 and the invoice is marked paid. Fixed by my PR, merged 17 Oct. #4540 · PR #4541
  • LNbits · fiat payments: a fiat invoice was failed after one hour while the provider's checkout was still payable, so a later payment was never credited. Fixed by my PR, merged 23 Oct into the development branch, not yet released. #4245 · PR #4246
  • PayU for WooCommerce: a COMPLETED payment notification was answered 200 but no longer completed the order, so the paid order stayed on hold or was cancelled as unpaid. Fixed by my PR, merged 23 Oct on the main branch, not yet released. #121 · PR #122
  • Paid Memberships Pro · Payfast: the payment notification was answered 200 before it was validated, so when the validation request to Payfast failed, Payfast never sent it again and the paid checkout was left unfinished, with no membership. Fixed by my PR, merged 27 Oct, released in 1.8: the notification now gets 503 so Payfast re-sends it. #113 · PR #114
  • Invoice Ninja · Razorpay: the Razorpay webhook handler is an empty stub, so when the customer closes the tab before the checkout posts back, Razorpay captures the payment but Invoice Ninja never records it and the invoice stays unpaid. Fixed by my PR, merged 29 Oct into the development branch, not yet released. #13394 · PR #13397
  • Charitable · PayPal Standard: when the postback that verifies an IPN with PayPal gets no answer at all, the listener still answers 200, so PayPal stops resending and the donation stays pending although the donor has paid. Fixed by the maintainers on 28 Oct, released in 1.8.14: an unanswered or non-2xx verification postback now answers 503, so PayPal re-sends the notification, while an INVALID answer still gets 200. Checked against the released code. forum topic
  • SumUp for Vendure: the pending fix waiting for the next release made adding a SumUp payment fail on every attempt, and the release that fixed amounts being charged 100 times too high had never reached npm. Fixed by the maintainer within a day, released in 0.3.1 on npm on 28 Oct. #48
  • Adyen for Magento 2 · split payments: the cause of “Full order amount has not been authorized”: authorised amounts were compared at a different precision than they are stored. Fixed by Adyen on 28 Oct on the main branch, not yet released: the amounts are now compared in minor units. Adyen closed my PR in favour of this fix. #3352 · PR #3379 · fix #3397
  • Vipps MobilePay for WooCommerce · subscriptions: when the response to creating a renewal charge was lost, the renewal was marked failed, but Vipps still took the charge and its webhook found no order, so the subscription went on hold. Fixed by the maintainer on 22 Oct on the main branch, not yet released. Checked against the fix: the renewal now stays pending and is paid once the charge is confirmed. #420
  • Invoice Ninja · SEPA, BACS, ACH, GoCardless: a subscription whose payment started as pending was never completed, so no recurring invoice followed. Fixed by the maintainers on 22 Oct, in the next release. #13343
  • BTCPay for WooCommerce: when the plugin cannot re-fetch a settled invoice from BTCPay Server, the webhook is still answered 200, so BTCPay never redelivers it and the paid order stays on hold. Fixed by the maintainer on 20 Oct, released in 2.8.6: the webhook now answers 503 so BTCPay redelivers it. #93
  • Bagisto · PayPal Standard: a buyer who paid but didn't return to the store got no order, and every retry of PayPal's notification failed with 500. Fixed by the maintainers on 15 Oct, listed in the changelog. #11531
  • Invoice Ninja · Stripe iDEAL, Bancontact, Klarna: no payment was recorded when the customer didn't come back from the bank. Fixed by the maintainers on 12 Oct. #13341
  • django-payments · Sage Pay: the return route crashed on every real redirect, so no payment was ever confirmed. Fixed by the maintainer on 11 Oct. #499 · PR #500
  • Odoo · Mollie: a failed status request to Mollie was acknowledged with 200, so the transaction stayed in draft. Fixed by Odoo on 8 Oct. #290678 · fix · case

Not counted above, since someone else reported the bug: in Standard Webhooks, the webhook signing spec, the Python library's sign() signed the wrong timestamp for a timezone-aware datetime outside UTC, so the receiver rejected every such webhook. Fixed by my PR, merged 28 Oct. PR #334

Confirmed, fix in progress (2)

  • Mollie for WooCommerce: the REST webhook answers 200 when the payment status can't be fetched, so Mollie stops retrying and paid orders stay pending. Confirmed by Mollie; they are preparing a patch. #1304 · case
  • Medusa · Stripe: the webhook signature is checked when the queued job runs, so a delivery already answered 200 is dropped if the job starts more than five minutes after Stripe signed it. My PR passed Medusa's automated review; a new rule closed it until the issue is assigned, which I have asked for. #17261 · PR #17262
