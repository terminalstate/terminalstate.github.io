AI features that behave on the bad day

I put language models into a production backend and make them behave when the input is ugly: output you can validate, timeouts and retries, tool calls that are safe to repeat, a ceiling on cost, and an eval on your own data. Python and Django, Celery, PostgreSQL — the same discipline that keeps a payment integration from charging twice.

Works in the demo, breaks in production?

A model feature that passed every eval and then returned the wrong thing under real inputs is rarely a model problem. A model call is one more external dependency you don't control: it times out, it answers twice, it hands back malformed JSON, and it can cost ten times on a bad input what it cost in the demo. Between the prompt and the row in your database there are a few places where that turns into a bug, and each one has its own check.

  1. The output isn't validated against a schema, so a malformed or half-empty answer is treated as success.
  2. A slow call blocks the request instead of going to a queue.
  3. A timeout or rate-limit isn't retried — or is retried without an idempotency key, so a tool action runs twice.
  4. Cost and tokens aren't capped or logged, so one adversarial input is a bill.
  5. There is no eval on your own data, so "it works" is a feeling, not a number.
  6. Nothing records what the model was asked and what it answered, so the one call that went wrong can't be debugged.

How a review starts

  1. You describe the symptom and send one call that went wrong — the input, what you expected, what came back. I reply with which of the places above it usually is, and what I would need to read.
  2. You export what you can: traces or logs of the calls, the prompt, a sample of real inputs. The first pass runs on those files, on your side if you prefer.
  3. Within a week: the document, an eval set built from your data, and a walk-through of both.

Public work

Six models on one contract-extraction task. The same prompt through six model APIs, scored against human labels on 83 public non-disclosure agreements. All six came out within noise of each other (F1 0.88–0.89), while the cost ran from $0.42 to $14.88 per thousand documents. Most of the remaining errors were made by most of the models at once, and read against the documents they come mainly from how the labels write names and define fields — which is why an eval starts with the definitions. Eleven first answers failed local validation — a bare year where a date belonged, a misspelled key, reasoning that ran out of room — so the check stays even when the API promises structure. Standard library, reproducible with one command. github.com/terminalstate/extraction-bench

The same task on a bad day. What happens around the answer: every output mechanism three model APIs offer, a repair for each kind of failure, and all 83 documents sent at once. Format failures followed each model's habits — one wrapped every answer in a code fence and kept doing it when asked not to — and a local repair fixed 98 of 99 of them for free; when the content was wrong, telling the model what was wrong fixed 20 of 20, a plain retry 7. With its thinking switched off, one model stopped cutting answers off, at less than half the cost and the same accuracy. The burst met no limit at one provider, a concurrency limit at another, and at the third a per-minute token limit that half the requests did not get past in five attempts. extraction-bench/reliability.md
